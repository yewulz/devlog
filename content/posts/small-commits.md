## 一次提交，讲清一件事

把一个完整且相关的改动组织成一次提交。避免把功能开发、无关的重命名和格式调整混在一起，让后来的阅读者能理解修改的目的。

提交说明不仅描述做了什么，也可以简短解释为什么。真正需要上下文的决定，值得留在记录里。

## 提交之前，再看一次差异

使用 git diff 阅读自己的修改。检查是否留下调试输出，是否带入意外生成的文件，是否有不该进入仓库的配置。

这个步骤就像发送一封重要邮件之前再读一遍。成本很低，却经常能够发现刚刚忽略的问题。

## 为实验建立独立分支

尝试新的布局或替换依赖时，用分支隔离尚未确定的工作。验证通过后再合并，可以让主分支始终保持一个清晰的状态。

分支不需要复杂的命名体系，只要能表达当前要完成的目标，就已经足够。

## 让历史帮助未来的自己

在排查问题时，清晰的历史能帮助定位行为从何时开始变化。好的版本管理不是提交越多越好，而是每次变化都有可理解的边界。

把审阅差异、运行必要检查和写清提交说明变成固定顺序，久而久之，它们就会成为开发的自然组成。

## 代码示例

```sh
git status
git diff
git add path/to/your-file
git commit -m "Explain the change clearly"
```
